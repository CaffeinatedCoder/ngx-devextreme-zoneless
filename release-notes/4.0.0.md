Entry-point isolation that holds under code splitting — the previous release was
costing a lazy-route consumer 1.7 MB it never imported — plus 40 new bindings that
close the demand-driven backlog, server-side rendering measured in CI, and three
fixes.

```bash
npm i ngx-devextreme-zoneless@4.0.0
```

## Breaking changes

- **The data-loading helpers moved out of `core` into `ngx-devextreme-zoneless/data-source`.**
  `dxArrayStoreSource`, `dxReloadOn`, `dxRemoteStore`, `dxLoadOptionsParams` and their
  types now come from the new entry point — or, as before, from the main entry, which is
  unchanged. Only an import from `ngx-devextreme-zoneless/core` has to move, a one-line
  edit. They construct `DataSource` and `CustomStore`, and `devextreme` declares no
  `sideEffects: false`, so that import cannot be shaken: kept in `core` it cost every
  chunk using any directive at all 44,984 B over the bare wrapper, 39,862 B of it
  DevExtreme's data layer. A sign-in page or a settings form gains roughly 10 KB brotli
  on first load.
- **`DxFieldStateDirectiveBase` takes the host instance, not its class token.** A
  subclass calls `super(injectDxHost<DxTextBoxComponent>())` instead of
  `super(DxTextBoxComponent)`, which is the same shape as every core base. The shipped
  `[dxFieldState]` directives are unchanged.

## Fixed

- **A directive no longer drags sibling widgets into a lazy route's closure.** Every
  family entry point imported the wrapper class of each widget it adapts, as the
  injection token for its host. esbuild assigns files to chunks by *reachability*, not
  by use, so a widget live for one lazy route was reachable from every other route
  sharing that FESM. Measured on 4.0.0's predecessor: a shell layout importing only
  `DxTreeViewSelectedNodeKeysDirective` from `/data`, next to a lazy page using
  `dx-data-grid`, carried the whole grid runtime in its static closure — 1,705,093 B
  raw / 325,755 B brotli on every first load, more than its own eager bundle. Wrapper
  classes are now type-only imports and the host resolves through the public
  `NestedOptionHost` token, so no entry point imports `devextreme-angular/ui/<widget>`
  at runtime and the only widget code in a bundle is what you import. In the probe that
  closure went from 2,836,967 B to 261,895 B. Behaviour is unchanged.

  Two findings worth keeping: it was never "importing `/data` costs grid + gantt +
  scheduler" — only widgets live *elsewhere in the same app* were dragged in, which is
  why a single-chunk tree-shaking probe could never see it. And an `export *` barrel
  over separate FESMs does **not** re-couple them, so the main entry point is not the
  trap; a shared FESM with a value import is.
- **`dxRemoteStore`'s `items()` now emits for a pushed update.** A real-time update
  pushed into the store is applied by *mutating* the array the `DataSource` already
  handed out, so publishing the same reference was an `Object.is` no-op: the grid
  re-rendered the change while `items()` silently never emitted it — measured as a grid
  cell reading 999 next to a readout still reading 87. The signal now gets a fresh array
  per publish. The vendor limit this exposed is not ours to fix: a paginated
  `DataSource` keeps only pushed updates, so `reload()` remains the route for inserts
  and removes.
- **The chart selection adapters no longer throw on the server.** With no `window`,
  DevExtreme builds every viz widget as an empty stand-in whose methods return nothing,
  and `[(dxSelectedPoints)]`'s initial read called `getAllSeries().flatMap(…)` on it
  from a timer — outside Angular's error handling, which is fatal to a Node server by
  default. Found by the new server-render measurement.

## Added

- **40 new bindings, every one with a reference screen and a both-direction e2e.**
  `[(dxOpened)]` for the drop-down editors and `dx-drop-down-button`;
  `[(dxExpandedNodeKeys)]` for `dx-tree-view`; `[(dxEditingChanges)]` and
  `[(dxEditRowKey)]` for the grids — the editing state DevExtreme designed for external
  ownership; `[(dxSelectionFilter)]` for deferred selection at remote scale;
  `[(dxVisualRange)]` and `[(dxValueAxisVisualRange)]` for `dx-chart`; `[(dxItemSizes)]`
  and `[(dxCollapsedItems)]` for `dx-splitter`; `[(dxZoomLevel)]` for `dx-calendar`;
  `[(dxValue)]` for `dx-file-uploader`; `[(dxFocusedRowIndex)]` for the grids; CardView
  and FileManager state; plus selection and paging breadth across tabs, accordion,
  button group, multi view, stepper, pagination, context menu and polar chart.
- **`items()` and `totalCount()` on the `dxRemoteStore` handle.** The loaded page and
  the server's count were observable only inside the widget; a header count or an
  empty-state message needed a second request. Both are now signals fed by the
  DataSource's `changed` event.
- **`injectDxHost<THost>()`** in `core`: the devextreme-angular component hosting the
  current element, without naming its class — what lets a wrapper stay a type-only
  import, and what every shipped directive now uses.

Every vendor claim behind these was verified against the installed sources before the
adapter was written, and the ones that could be normalised or partially rejected re-read
after their own write. Three options are documented as **not bindable** rather than left
to discovery: the scheduler's `selectedCellData` and the grids' `focusedColumnIndex` are
written by the widget but ignored on the way in, and Map centre/zoom, Diagram and
ScrollView have silent setters or methods only.

## Tests

Every *directive* is now driven through the zoneless app, not merely every family: two
coverage screens place one row per directive the binding screen does not, which is how
the two defects above that had no coverage at all were found. `npm run probe` guards
isolation under code splitting with a six-lazy-chunk app, not just a static scan.
`npm run ssr` renders every screen under `@angular/platform-server` in CI and fails on a
throw, a hang or a late error. A signal read inside a widget-rendered `*dxTemplate` is
pinned to re-render with no zone.

## Not in this release, by decision

`dx-tab-panel[dxSelectedItemKeys]` was built, failed its signal → widget case and was
withdrawn rather than shipped unproven — a tab panel's selection is single by
construction and `[(dxSelectedIndex)]` already owns it. CRUD on `dxRemoteStore` stays
deferred, and a `testing` entry point waits for demand. There is no `ng update`
migration: the breaking change moves four symbols' import path, and the main entry keeps
exporting them unchanged.
