A grid's complete row and column axes as signals, the compatibility net moved onto
DevExtreme 26.1.6 and Angular 22.2.3, every example in the package off the vendor's
deprecated nested configuration components, and one summary-recompute fix. Peer ranges
are unchanged, so there is nothing to do on upgrade.

```bash
npm i ngx-devextreme-zoneless@4.1.0
```

## Added

- **`dxGridRows` / `dxGridColumns` — a grid's complete row and column axes, in display
  order** (`ngx-devextreme-zoneless/data`). Both of DevExtreme's public readers are
  windowed under virtual rendering: measured on a 60 × 20 grid, `getVisibleRows()`
  answers 16 of the 60 rows and `getVisibleColumns()` 6 of the 20, and the windowed
  column list carries virtual spacer entries at its ends. Anything that works past the
  edge of the screen — a range selection, a fill handle, an export of what the user sees
  — cannot be built on them. Both take a `dx-data-grid` or `dx-tree-list` instance and
  infer that widget's own `Row` and `Column` types. `dx-card-view` deliberately does not
  fit: with no virtualization its own `getVisibleCards()` is already complete for the
  page. Two limits are documented rather than hidden: "complete" means *loaded*, not the
  whole dataset, and `dxGridColumns` answers `[]` while `stateStoring` is still loading.

## Changed

- **Built and verified against DevExtreme 26.1.6 and Angular 22.2.3**, up from 26.1.4
  and 22.1.3. **Peer ranges are unchanged** — `@angular/core >=22.1 <23`,
  `devextreme`/`devextreme-angular >=26.1` — so there is nothing to do on upgrade; what
  moved is what the compatibility net actually exercises. Worth knowing because 26.1.5
  and 26.1.6 were not quiet patch releases: they split state storing, added a
  data-source controller, renamed the TreeList data controller and deleted
  `m_virtual_data_loader.js`. All four gates are green on them, and `totalItemsCount()`
  changing controllers broke exactly one test helper and no shipped code.
- **Every example in this package, and the library's own TSDoc, is off DevExtreme's
  deprecated nested configuration components.** `W3001` is
  `LEGACY_CONFIG_COMPONENT_USED`, so copying an example from here was handing you a
  spelling the vendor asks you to stop using — and the TSDoc ships in `dist/types`,
  which is where you read it on hover. `<dxo-selection>` is now
  `<dxo-data-grid-selection>`, `<dxi-column>` is `<dxi-data-grid-column>` or
  `<dxi-tree-list-column>` depending on the widget it sits in, and so on, across 109
  occurrences in the reference screens, the TSDoc, the README and the directive catalog.
  **No import of yours has to change** — the named components are the same generated
  classes and every widget module already exported them, and nothing about the bindings
  changed. Measured: `W3001` is now 0 across all six screens, and `/coverage` renders
  byte-identical HTML in Node.

## Fixed

- **`[(dxEditingChanges)]` now recomputes a DataGrid's summaries where a typed edit
  does.** With `summary.recalculateWhileEditing` on, the grid recomputes its group and
  total summaries when the *user* edits a cell, while a change written from the signal
  recomputed nothing. The same pending change therefore rendered two ways depending on
  who set it: the modified cell appeared, the footer kept the pre-change total. The
  binding now runs the vendor's own recompute after a signal-side write, over the rows
  the grid already holds.

  **Nothing changes at the default.** `summary.recalculateWhileEditing` is `false` out
  of the box, and the grid then totals saved data deliberately, so the binding stays
  inert there — pinned by its own e2e case rather than left to reasoning. Two limits are
  the widget's and not the binding's: under `remoteOperations.summary` the server owns
  the numbers and cannot know your pending changes, and `cacheEnabled: false` makes the
  recompute re-read the store, exactly as it does when the user types. `dx-tree-list`
  has no `summary` option, so nothing there changes.
